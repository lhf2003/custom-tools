# 视频片段向量化失败修复（代理超时 + decord 换 PyAV + 帧预算降载）

**创建日期**: 2026-08-31
**作者**: LHF + Claude
**版本**: v1.2
**状态**: 已修复并验证

## 症状

浏览器扩展能捕获视频画面分片（MediaRecorder 正常产出 10s webm），但向量化必败。
先后暴露三个错误：

1. `sidecar 通信失败: WeMM 主实例连接断开`（文本/图片模态不受影响，只有视频挂）
2. `decord video_reader.cc:270: Failed to measure duration/frame-count due to broken metadata`
3. `CUDA out of memory`（15.3GB allocated by PyTorch，8GB 卡）

## 根因一：两层超时夹击一个 130 秒的视频 embed

1. **sidecar 代理模式 socket 超时残留**（主因）：`socket.create_connection(..., timeout=5)`
   的 timeout 会残留在 socket 上作用于后续所有 recv/sendall。视频 embed 远超 5s，
   代理等 5s 即 socket.timeout（OSError 子类）→ 误报「主实例连接断开」。
   文本/图片 embed <5s 能侥幸通过，所以只有视频挂。
2. **扩展 callNative 60s 超时**（次要）：`background.js` video_segment 超时 60s，同样不够。

## 根因二：decord 帧索引路线与 MediaRecorder webm 不兼容

真实浏览器录制的原始 webm：unknown-size Segment/Cluster + 无 Duration + 无 Cues。
中间曾移植参考仓库（xiaotianfotos/indexed）的 fix-webm-duration（注入 Duration 头），
对 Playwright 仿真文件有效，但对用户真实文件**修复后 decord 仍失败**——decord 需要
建立帧索引/计数，容器层修补治标不治本。PyAV 顺序解码完全不依赖容器元数据，直接可读。
（早期验证通过的测试文件其实是带完整头的文件，不具代表性；后用取证落盘拿到用户
真实样本才定位——该取证机制保留在 embed_media 中，解码失败写 %TEMP%\nervis_wemm_debug\）

## 根因三：孤儿 sidecar 占满显存 + 720p×32 帧视觉 token 超 8GB 预算

- 测试/浏览器反复拉起杀死的 sidecar 进程不会释放显存（kill host 不级联），
  僵尸进程抱 5.1GB 模型显存 → 后续 embed 必 OOM，报错像激活值问题，实为抢占。
- 即使干净环境，模型 5.1GB + 桌面/浏览器 ~1.5GB 后，720p×32 帧 ≈ 2.9 万视觉 token
  的激活值超出 8GB 物理预算（WeMM 处理器 video longest_edge=224MP 基本不缩放）。
  降载 640×360×24 帧 ≈ 5.5k token 后 embed 从 130s 降到 **~3-5s**，两头都解。

## 最终修复

- `sidecar/wemm/server.py`
  - proxy_mode 连接成功后 `sock.settimeout(None)` 解除残留超时
  - 视频解码 decord → **PyAV 顺序解码 + 内存均匀抽帧**（`_read_video_frames`）
  - 帧预算常量化：`VIDEO_NFRAMES=24, VIDEO_MAX_W=640, VIDEO_MAX_H=360`，
    主实例启动日志带帧预算标记（一眼识别服务进程代码版本）
  - 解码失败取证落盘 `%TEMP%\nervis_wemm_debug\`（浏览器链路 stderr 不可见）
  - 协议回落为 `embed_video {video_base64, mime}`（修复方案变更后不再需要 captured_seconds）
- `extension/background.js`：video_segment 的 callNative 超时 60s → 300s
- `sidecar/wemm/pyproject.toml`：依赖 `qwen-vl-utils[decord]` → `qwen-vl-utils` + `av==18.1.0`；
  torch/torchvision 源改为仓库内本地 wheel（与 uv.lock 实际一致；阿里云 pytorch-wheels
  非 simple 布局、包页 404，索引源形式从未可解析）
- `sidecar.rs` / `memory-host.rs` / `video-frame.js`：无 net 变更（中间方案已回退）

## 验证

- Playwright 真实 Edge 通道录制（Chromium 同款 muxer）：复现 decord 270 → PyAV 可读
- 用户真实失败样本（取证落盘的 orig.webm，252KB B站录制）：PyAV 37 帧全解码
- 端到端 release host → sidecar（主实例/代理两路径）：均 `ok:true`
- 干净环境显存 456MiB 起步，embed 全程 16-20s（含模型加载）

## 踩坑记录

- cargo build 管道接 tail 会吞非零退出码；构建后必须核对 exe mtime
- 浏览器扩展 keepalive 持续拉起 memory-host，exe 常驻被锁；rename 运行中 exe 合法可绕过
- 杀 host 不级联杀 sidecar → 孤儿占端口/显存跑旧代码；清场以 nvidia-smi 显存回落为准
- Windows WDDM 不支持 expandable_segments（设了只有 UserWarning，已撤）

## 遗留问题（待裁决）

   pyproject 时 torch 走本地 wheel 路径会失败（wheel 未打包）。需裁决：打包 wheels（+2.5GB）、
   生产用 direct-URL 源、还是随包带 uv.lock + 预填缓存。本机存量 venv 不受影响。
2. **检索质量回归**：640×360×24 的视觉预算未经 N0 式回归验证，建议后续 spike 对比
   （候选档位 448×252×16 / 854×480×32）。
