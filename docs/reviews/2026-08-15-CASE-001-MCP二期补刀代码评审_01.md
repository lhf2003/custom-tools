## CRITICAL（2）

### C1. stdio 启动配置无转义拼入 cmd /s /c 串 → JSON 导入即任意命令执行

**位置**: `src-tauri/src/companion/mcp_stdio.rs:59-75`

`spawn_args` 把 env 的 `set "K=V"&&` 语句与 args 原样拼成 `cmd /s /c <串>`，参数中的 `"` `&` `|` `%` 全部按 cmd 语义解释。JSON 导入（`parse_server_entry`）与手动配置都可携带 args/env → 点「验证并添加」→ `probe_stdio`（L79）立即 spawn → **注入命令以当前用户权限执行**。

**已实测复现**（本机真实 cmd，与 Rust 侧 `Command::new("cmd").args(["/s","/c",full])` 等价，均输出 `23851`）：
- args 注入：arg 元素 `"x"&whoami&""` → `npx -y "x"&whoami&""`
- env key 注入：key 为 `K" & whoami & "` → `set "K" & whoami & "=v"&&npx -y`
- env value 注入：value 为 `a" & whoami & "` → `set "K=a" & whoami & ""&&npx -y`

更恶意的构造可静默写启动目录、删文件（`&` 无条件执行，前置命令失败与否无关）。

**修复**: env 改经 `Command::env()` 注入（完全绕开 set 串）；args 逐参数按 cmd /s /c 引号规则转义（内嵌 `"` 加倍、`%` 转 `%%`、禁 `&|<>` 换行等控制字符，配置保存时校验兜底）；`.cmd/.bat` 走 cmd /c 的方向正确，组装姿势必须修。

### C2. 读超时被 `thread::scope` join 语义废掉 → 卡死 server 永久挂起 + 全局锁连带死锁

**位置**: `src-tauri/src/companion/mcp_stdio.rs:189-208`

`rx.recv_timeout(30s)` 超时返回 Err 后，`std::thread::scope` 退出前必须 join 阻塞在 `read_line` 的读线程——server 活着但不写 stdout（`npx -y` 首次下载依赖、server 内部卡死）时线程永不返回，**rpc 无限期阻塞**，30s 兜底实际不生效。此时 `call_stdio_tool`（L105）全程持有全局 REGISTRY Mutex：该 server 后续所有调用、`evict()`（停用/删除/刷新）、`shutdown_all()`（应用退出）全部连带挂死；每次挂起还永久占用一个 spawn_blocking 线程，多次后阻塞线程池耗尽波及全应用（websearch/shell 等所有 spawn_blocking 任务饿死）。与注释承诺「不能拖死聊天工具轮」正好相反。

**修复**: 读线程不放进 scope——独立 `thread::spawn` + channel，超时分支先 `kill_tree()`（EOF 使读线程立即返回）再返回错误；或改 tokio 异步读。

## HIGH（4）

### H1. 直接 spawn 分支（.exe/带路径命令）静默丢弃 env 配置

**位置**: `src-tauri/src/companion/mcp_stdio.rs:61-62`

`if !wrapped { return (program, args.to_vec()); }` 完全忽略 env 参数。command 为 `node.exe` 或 `C:\...\node.exe` 的 server，设置页配置的 API_KEY 等环境变量静默不生效，server 启动失败/未授权且无任何提示。

**修复**: `!wrapped` 分支用 `cmd.env(k, v)` 逐项传递。

### H2. full 串经 `.args()` 传递走 MSVCRT 转义，含空格参数被 cmd 拆散

**位置**: `src-tauri/src/companion/mcp_stdio.rs:74-75`（对照 shell.rs:647-658 先例）

shell.rs 明确注释「不能用 .arg()，会做 MSVCRT 转义，cmd 不认」，用 raw_arg 手工包外层引号；本文件用 `.args()` 传 full 串。参数本身含空格（如 `"D:\my data"` 目录）时被 cmd 按空格切成多个参数。测试 `spawn_args_wraps_cmd_with_quotes_preserved`（L290-301）断言「a b」不加引号拼入并把「引号保真」写进注释——等于把 bug 固化成测试。

**修复**: 与 C1 合并修——仿 shell.rs 用 `raw_arg` 整体传外层引号包裹的串，参数内层按 cmd 规则转义。

### H3. stdio 响应不校验 id、不跳过杂行 → 通知/banner 被当响应，结果错配或 server 永久不可用

**位置**: `src-tauri/src/companion/mcp_stdio.rs:197-208` + `mcp_client.rs:301-311`

读一行即 `unwrap_rpc_envelope`，不检查 `msg.id == 请求 id`；且该函数对「无 error 无 result」的通知返回 `Ok(Value::Null)`（非错误）。两类后果：
1. server 合规发出的通知行（`notifications/message` 等）被当 tools/call 响应 → 模型收到空文本（静默成功），真实响应残留在管道 → 下一次调用消费上一次的响应 → 结果错配。
2. 启动往 stdout 打 banner/日志的 server（python print、部分 SDK）→ 第一行解析失败 → 报错重试 → 新进程再打一遍 banner → 「重建会话后仍失败」，该 server 工具调用 100% 失败且重启应用无效。

HTTP 路径 `parse_response_body` 有按 id 过滤（SSE 分支），stdio 缺失，不对称。

**修复**: rpc 循环 read_line，跳过非 JSON / 无 id / id 不匹配的行（设跳过上限防死循环），直到匹配。

### H4. probe_stdio 错误路径不杀进程树 → 导入/刷新失败累积孤儿进程

**位置**: `src-tauri/src/companion/mcp_stdio.rs:86,93`

initialize / tools/list 失败时直接 `return Err`，session 未入 REGISTRY 也未 kill_tree，npx→node 进程树残留（携带配置 env 注入的密钥）。每次失败的导入/刷新验证都遗留一棵，`shutdown_all` 只清 REGISTRY 管不到。

**修复**: 错误路径统一 `kill_tree()`（RAII 守卫或 match 后清理）。

## 结论与建议

**决策：BLOCK**。C1（命令注入，已实测）与 C2（全局死锁）必须修复；H1-H4 与 C1/C2 同源（都在 mcp_stdio.rs 的 spawn 组装与 rpc 读路径），建议合并一次改完。

建议修复顺序：

1. **第一批（安全边界，C1/H1/H2 同函数）**：spawn_args 重构——env 走 `Command::env()`、args 按 cmd 引号规则转义、配置保存时校验 key/value 禁控制字符；补 C1 三构造的回归测试（真实 cmd，与 shell.rs 集成测试同姿势）
2. **第二批（可靠性）**：C2（超时真实现：独立读线程 + 超时先杀树）、H3（id 校验 + 跳行上限）、H4（probe 错误路径杀树）
3. **第三批（收尾）**：M1/M2（日志写入与保留策略）、M3（clippy 绿化 + MSRV）、M6（凭据语义）、M4/M5（错误提示）
4. 其余 MEDIUM/LOW 按节奏排期

正面结论：SQL 全部参数化；调用日志只存元数据（不落请求/响应/token）；`to_info` 凭据值不下发（只给 key 名）；get_settings 脱敏未回归；前端无 XSS/注入面（无 dangerouslySetInnerHTML）；无状态 mutation 违规；HTTP 通道改动（headers 数组化、会话重初始化）正确；`jarvis_chat_is_generating` 简单安全；退出清理挂 RunEvent::Exit 与 websearch 同姿势；测试覆盖 202 全过。
