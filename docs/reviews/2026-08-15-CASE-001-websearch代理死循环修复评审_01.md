## 背景与正确性核对

问题根因（日志实证）：reqwest 0.13 默认读 Windows 系统代理且不尊重注册表 ProxyOverride 的 `127.*` 绕过列表，导致本地 daemon 的 `/health` 请求被 Clash（127.0.0.1:7892）拦截，健康检查 120 秒内全部失败（实测 3721 端口 59 次、3722 端口 105 次连续失败），模型每轮拿到超时错误后又调用 web_search，形成 120 秒 × 50 轮上限的"永不停止"循环。

修复正确性：
- ✅ `.no_proxy()` 是 reqwest 0.13.2 的稳定 API，禁用环境变量与系统代理检测，loopback 直连语义正确
- ✅ 两处 client（搜索请求 + 健康检查）均已覆盖，无遗漏路径
- ✅ 修复后健康检查首次即成功，daemon 句柄会被复用，不再重复 spawn 新端口
- ✅ 前端查询的是 FIFO `in_flight`（含排队中），ChatView 所有 mode 均走 `jarvis_chat_send_scene`（ChatView.tsx:843），查询覆盖完整

### MEDIUM

**M1 — 挂载恢复存在事件丢失竞态窗口**（ChatView.tsx:423-428 与 :614 监听注册 effect）

时序：组件卸载期间后端完成回复并 emit `jarvis:done` → 用户切回视图 → 挂载查询返回 `true`（emit 时 `in_flight` 尚未复位）→ 但 done 事件已无人监听 → `isLoading` 卡在 true。窗口毫秒级（done emit 与 FlightReset drop 之间），且存在自愈路径：卡住时点取消按钮（`handleCancel` 里 `setIsLoading(false)`）即可恢复。

建议：查询返回 true 时挂短兜底定时器（约 2~3 秒后重查一次，`in_flight=false` 则复位），把该窗口彻底关掉。

**M2 — 同类代理劫持隐患未覆盖：HTTP 类型第三方 MCP server**（mcp_client.rs:67）

`McpHttpClient` 经 `build_client` 建 client；在 `system_proxy_enabled=false` 时工厂不附加 loopback 绕过，reqwest 0.13 默认读系统代理——接入 `http://127.0.0.1:xxx` 的本地 HTTP MCP server（本地服务场景常见）会与本次 bug 同因挂死。注意不能在 `build_client` 全局 `.no_proxy()`（LLM 调用依赖默认系统代理行为连通 deepseek），需按请求 URL 判断：loopback 目标单独直连。

### LOW

**L1 — websearch.rs 每次调用新建 reqwest client**（websearch.rs:74、:299）

`POST /search` 与 `health_ok` 每次调用都 build 新 client，连接池不复用；健康检查失败路径下 120 秒循环会建上百个 client。修复后健康检查一次即成功，实际影响微小；可考虑 `health_ok` 用 `OnceLock` 静态 client 复用。
