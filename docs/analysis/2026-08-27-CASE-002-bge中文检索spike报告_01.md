## 结论（先说答案）

**bge-small-zh-v1.5 fp32 作为一期出货模型，全链路技术假设成立。** 纯 Rust（`ort` + `tokenizers`）+ ONNX 本地推理，CPU 即可，无需 GPU、无需 Python。

| 验收线 | 目标 | 实测（small-zh fp32） | 判定 |
|---|---|---|---|
| top-3 命中率 | ≥ 70% | **88%**（14/16） | ✅ |
| top-1 命中率 | 参考 | **81%**（13/16） | ✅ |
| 语义查询延迟 | P95 < 500ms | **P95 31ms / P50 7ms**（CPU） | ✅ 余量 16 倍 |
| 安装包增量 | < 100MB | **95MB**（模型 fp32 本体） | ✅ |
| 索引吞吐 | 后台可接受 | 34ms/doc（batch 16） | ✅ |

## 三模型对比（同一语料 488 条、同一查询集 16 条）

| 模型 | 体积 | top-1 | top-3 | embed/doc | query P50 |
|---|---|---|---|---|---|
| bge-base-zh-v1.5 fp32（768d） | 410MB | 69% | 88% | 141ms | 17ms |
| bge-base-zh-v1.5 int8（Xenova 社区导出） | ~100MB | 12% | 19% | 81ms | 29ms |
| **bge-small-zh-v1.5 fp32（512d）** | **95MB** | **81%** | **88%** | **34ms** | **7ms** |

## 关键发现

1. **社区量化导出不可信，必须自验**：Xenova int8 导出分数全部压进 0.84-0.88 窄带（锥形坍缩），区分度全毁。fp32 正常。教训：任何量化权重接入前必须过一遍本评测集；且**相似度阈值必须按模型实测标定**（此案例是设计 D9「阈值不拍脑袋」的活体证据）。
2. **small 在 488 条个人语料上 top-1 反超 base**（81% vs 69%）：小语料下小模型不输，且 95MB 天然满足安装包预算，无需冒量化风险。
3. **「漏检」多半是元数据问题不是向量问题**：3 条 top-3 未中里，2 条实际命中了语义等价的备选（「休息日刷剧」命中另一个同样刷剧的周日；「燃气 curl」命中同一 API 的 UAT 环境版本）。真正需要的是**时间衰减 + 元数据过滤**（设计已含），向量层无罪。
4. **512 token 截断是硬边界**：超长文档必须在索引侧切块（导出脚本已按 1200 字符切块），推理侧截断兜底。
5. **ort `load-dynamic` 复用 pip 版 onnxruntime.dll**（1.28.0）零网络下载，绕开国内拉取 ORT 二进制的坑；出货时改为随包分发 DLL 或静态链接，实现期再定。

## 评测方法

- 语料：`scripts/export_spike_corpus.py` 从现役 flowhub.db（剪贴板 447 文本条）+ notes 目录（49 篇）导出 488 条，超长文档 1200 字符切块。
- 查询集：16 条「记得语义不记得关键词」的描述性查询（`spikes/bge-onnx/corpus/queries.jsonl`），人工标注期望文档。
- 查询侧加 bge-zh 官方指令前缀「为这个句子生成表示以用于检索相关文章：」，文档侧不加；CLS 池化 + L2 归一化，暴力余弦 top-k。

## 对 M1 的输入

- 模型：`bge-small-zh-v1.5` fp32 + 官方 tokenizer.json，随包分发（95MB）；base-zh 可作为「高质量模式」可选下载，不做默认。
- 推理栈：`ort =2.0.0-rc.13`（load-dynamic）+ `tokenizers 0.21`，embed 批量 16、截断 512。
- 评测集与 spike 工程保留在 `spikes/bge-onnx/`（产物已 gitignore），后续换模型/换量化先跑这套回归。
