# run_shell_command 权限黑名单化与工具调用上限 50 设计

**创建日期**: 2026-08-14
**作者**: LHF × Claude
**版本**: v1.0
**状态**: 已批准（/grill-me  grilling 裁决）

## 背景

无打扰模式（unattended）原实现为「默认拒绝 + 只读白名单放行」：整串命令含任何壳元字符（`& | > < \` ;`）即弹窗。审计表（shell_confirm_audit 近 30 条，全部 unattended、全部用户手动允许）显示弹窗集中在三类误伤：

1. **只读探测 + 壳组合符**（约 2/3）：`dir /s /b ... 2>nul & dir /b ...`、`tasklist ... | findstr /I "qq"`、`where X || where X.exe`——模型天然爱用组合符拼接只读探测。
2. **白名单未覆盖的只读命令**：`reg query`、`wmic product ... get`。
3. **启动程序类**：`start QQMusic`、`powershell -Command "Start-Process ..."`——找 QQ 音乐一回连弹 8 次。

同时发现**现存漏洞**：shell 侧无敏感路径检测，unattended 下 `type %USERPROFILE%\.ssh\id_rsa` 静默放行（type 在白名单、无元字符即过）。

## 裁决

### D1 安全模型翻转（仅 unattended）

从「默认拒绝 + 白名单」翻转为「默认放行 + 黑名单」，三层结构：

| 层 | 内容 | 行为 |
|---|---|---|
| 硬拒绝（保持现有） | diskpart/shutdown/bcdedit/takeown/icacls/format；del\|rd\|rmdir + /s；reg delete；net user/localgroup；cipher /w；rm -rf | 任何模式直接拒，用户确认也救不回 |
| 确认名单（新增） | 见 D2 | 弹系统原生确认框（机制与审计表不变） |
| 其余全部放行 | 只读查询、`& && \| ||` 任意组合、运行脚本/构建命令、`start`/exe 路径启动程序、mkdir/rmdir（无 /s） | 静默执行 |

判定方式：**整串 token 扫描**（与现有 hard_deny 同一套，位置无关），嵌套 `cmd /c "del ..."` 里的危险词照样命中，不做拆段解析。

confirm_all / accept_edits 两档不动。

### D2 确认名单粒度

1. 删除/覆盖动词：del/rd/rmdir（无 /s）、copy/move/ren/xcopy/robocopy/replace/attrib
2. 写重定向 `>` `>>`（`2>nul`、`>nul`、`2>&1` 丢弃型放行）
3. 包管理安装：npm/pip/cargo/winget 的写子命令（install/add/remove/uninstall/update 等）
4. git 写子命令：commit/push/reset/clean/checkout/switch/restore/rebase/merge/add/rm/mv/stash 等（status/log/diff/show/blame/branch/tag/remote/ls-files/fetch/clone 放行）
5. reg add（reg delete 已在硬拒绝）
6. taskkill
7. 解释器内联代码：python -c、node -e、powershell/pwsh 整词、bash/sh 整词
8. 下载到文件：curl 带 -o/--output、Invoke-WebRequest/-OutFile

**间接执行放行**（D3）：`python xx.py`、`npm run build`、`.\xx.bat`、`cargo run` 等运行文件/构建命令放行——写毒脚本会在写文件那环被重定向弹窗暴露，有可接受兜底；拦它们则日常开发回到弹窗地狱。

### D4 启动程序放行 + 工具描述引导

`start`/exe 路径静默放行（含 `start http://...`）；**不为 powershell Start-Process 开特例**（内联代码开口子 = 黑名单破窗）。在 run_shell_command 工具描述中引导：启动程序用 `start "" "路径"` / `start 程序名`，不要用 PowerShell；读文件内容优先 read_file。

### D5 敏感路径补洞

shell 命令先环境变量展开（复用 read_file 的 expand），命中敏感片段（.ssh/.gnupg/.aws/.azure/.kube/.docker、id_rsa/id_ed25519/id_ecdsa/id_dsa、.git-credentials/.netrc/.npmrc/.pypirc/.env、浏览器凭证、flowhub.db）：

- 自动模式（accept_edits/unattended）：直接拒绝，文案引导切默认模式
- confirm_all：走弹窗

与 read_file 语义对齐。宁宽勿窄（漏过代价 = 密钥上云）。

### D6 工具调用上限 10 → 50

`MAX_TOOL_ROUNDS = 50`（scene_chat.rs），轮次语义、硬编码，到顶强制收尾（不带 tools 再问一次）不变。修正 scene_chat.rs:209「上限 4 轮」过时注释。失控防护三层不变：强制收尾 / 用户取消 / llm_call_logs 审计。

### 不做清单

- 不做「本会话放行同类」按钮（三层结构已覆盖降噪需求）
- 不做 launch_app 专用工具（start 放行已覆盖）
- 不做用户可编辑名单（硬编码，设置页只读展示名单摘要）
- read_file 现有行为不动

## 附：实施验收时抓出的执行层 bug（已修）

黑名单上线后首轮实测（「打开QQ音乐」场景）暴露一个**更底层的存量 bug**：
`run_command` 用 `.arg(format!("chcp 65001>nul & {}", command))` 传参，
`.arg()` 对内层引号做 MSVCRT 转义（`\"`），而 cmd 不认这套转义——
**任何含引号的命令都被肢解**（报「拒绝访问」「系统找不到指定的路径」），
而路径带空格必须加引号，等于所有带空格路径的操作全灭。
此前白名单模式下这些命令同样失败，只是弹窗让人能逐条看到；黑名单静默化后
失败不可见，模型只会误判「路径不存在」。

修复（shell.rs `run_command`）：`cmd /s /c` + `raw_arg` 原样直传 + 手工包最外层
一对引号——`/s` 让 cmd 剥掉最外一对引号后逐字执行中间内容，引号/&/| 全部保真。
已补 Windows 集成回归测试（真实起 cmd 验证带空格路径/引号内元字符/组合命令）。

经验：**执行层零测试是这个 bug 活过白名单时代的原因**；权限层测试再全也拦不住
执行层把命令改坏。
