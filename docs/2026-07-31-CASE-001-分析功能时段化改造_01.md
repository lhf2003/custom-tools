# 分析功能时段化改造设计

**创建日期**: 2026-07-31
**作者**: LHF + Claude
**版本**: v1.0
**状态**: 已批准

## 背景与动机

陪伴模块的「分析功能」目前每天晚上 21 点随日报链路触发一次，存在两个问题：

1. **频率低**：一天只跑一次，习惯模式与事实沉淀的新鲜度滞后一整天。
2. **数据空缺**：21 点触发的日报/日记覆盖「今天 00:00–21:00」，21:00–24:00 的活动永远进不了任何一天的日报。

改造目标：模式挖掘一天四触发（9 / 14 / 18 / 0 点），真实对应用户一天的时间段；日报、日记、明日关注移到 0 点触发，覆盖完整自然日。

## 现状梳理（改造前）

`src-tauri/src/companion/analyzer.rs::run_scheduler` 每分钟循环，两条调度线：

- **21 点块**（`DAILY_ANALYSIS_HOUR = 21`，`companion_last_analysis_date` 日期粒度防重）：
  模式挖掘（分析昨天全天）→ recall 记忆提取兜底 → 情感日记 → 明日关注 →（周日）自评。
- **日报独立线**：触发时刻从 `reporter.md` frontmatter `schedule: daily 21:00` 读，
  `companion_last_report_date == today` 防重，失败每 30 分钟节流重试，启动时 `maybe_backfill_report` 补昨日缺报。

关键机制：

- `upsert_pattern`：同签名冲突时 `occurrences + 1`，满 2 次 `learning → confirmed`（一天一次分析 ⇒ 2 天确认）。
- `run_daily_analysis`：固定分析昨天 00:00–24:00；活动 <10 条跳过（不送 LLM）。
- `seed_skills` 只播种不迁移：已有 `reporter.md`/`analyst.md` 不会被内嵌默认值覆盖。

## 总体方案

### 任务拆分

| 任务 | 现状 | 新方案 |
|---|---|---|
| 模式挖掘 | 21 点 ×1，分析昨天全天 | 9 / 14 / 18 / 0 点 ×4，增量水位线窗口 |
| 日报 / 日记 / 明日关注 | 21 点，覆盖「今天」 | 0 点，归属后移覆盖「昨天全天」 |
| recall 兜底、周日自评 | 挂在 21 点块 | 挪进 0 点块 |

### 模式挖掘四触发

- **窗口：增量水位线**。新增设置键 `companion_last_analysis_ts`，每次分析「上次水位到现在」的数据，
  跑完推进水位。自然形成 9 点看 0–9、14 点看 9–14、18 点看 14–18、0 点看 18–24 的分段；
  app 中途没开水位自动顺延，不丢不重。
- **slot 防重**：slot key 格式 `YYYY-MM-DD#HH`（如 `2026-07-31#14`），持久化到 settings；
  当前时间 ≥ slot 时刻且该 slot 未跑过才触发。**错过多个 slot 只补最新一次**
  （水位线机制下错过的数据已并入本次窗口，逐个补跑只会重复送同一批数据）。
- **时刻配置**：`analyst.md` frontmatter 增加 `schedule: daily 09:00,14:00,18:00,00:00`；
  `skills::parse_schedule` 扩展支持逗号多时刻（`Schedule::Daily` 由单时刻改为时刻列表）。
  手册 `enabled: false` 时不调度；文件丢失/无 schedule 回退硬编码 `[9,14,18,0]`——手册丢了分析也不丢。
  `DAILY_ANALYSIS_HOUR` 常量退役。
- **prompt 带窗口边界**：聚合摘要前注明「这是他今天 09:00–14:00 的使用情况」（跨天则写全起止），
  替换原写死的「昨天」，避免 LLM 对 `time_window` 的臆测。
- **空转零成本**：保留「活动 <10 条跳过」守卫，9 点窗口（睡眠时段）大概率不送 LLM。
- **手动按钮**：`analyze_companion_now` 从「分析昨天全天」改为水位线语义「补分析到当前时刻」。
- **水位线初始化**：`companion_last_analysis_ts` 缺失时初始化为昨天 0 点，
  与旧机制（昨晚 21 点分析昨天全天）干净衔接，昨晚没跑过的昨天数据也不漏。

### 模式确认节奏：按天去重

分段后同一贯穿全天的组合会在 4 个窗口各 sighting 一次，`occurrences` 语义从「天数」稀释为「窗口数」，
确认从 2 天提速到 1 天。对策：同一天内同签名再次 upsert 时只更新
`description`/`pattern_data`/`confidence`/`last_seen`，**不累加 `occurrences`**——
守住「occurrences = 天数、2 天确认」的现有语义。分段只提升数据新鲜度，不改变毕业节奏。

实现：`upsert_pattern` 的 `ON CONFLICT` 分支增加 `last_seen` 是否今天的判断
（SQL 层用 `date(last_seen,'unixepoch','localtime')` 与当前日期比较）。

### 0 点统一块与日期归属后移

0 点 slot 触发一条**顺序流水线**（单线程顺序执行，避免 0 点整多路 LLM 并发）：

```
模式挖掘(18–24 窗口) → recall 兜底 → 日报(昨天) → 日记(昨天) → 明日关注(新一天) → (周日)自评
```

- **归属后移**：0 点时「今天」无数据，日报/日记覆盖**昨天全天**（含 21–24 点原空缺），
  明日关注面向**刚开始的新一天**（用户早上看到的关注清单即当天清单）。
- **日报守卫**：`companion_last_report_date` 的判定与写入从「今天」改为「昨天」；
  手动生成按钮的「标今日完成」同步改「标昨天完成」。
- **重试与补跑**：日报首次运行并进 0 点块；失败仍由独立调度线每 30 分钟节流重试；
  启动时 `maybe_backfill_report` 逻辑不变（昨天缺报则补）。0 点前关机的早睡日，
  日报在次日启动时补跑，呈现为「晨报」——符合预期。
- **reporter.md**：schedule 从 `daily 21:00` 改为 `daily 00:00`（用户机器上的文件一并修改；
  单用户工具，无需迁移兼容逻辑）。

### 其他联动

- recall 兜底、周日自评从 21 点块挪入 0 点块（跟随链路，不单独时段化）。
- `emotion::on_report_done`、`on_late_night`、`CLEANUP_HOUR = 3` 等机制不变。
- LLM 路由（CC 优先、失败回退场景模型）与观测登记（`llm_call_logs`）不变。

## 成本评估

LLM 调用约 4 次/天 → 6–7 次/天（分析 ×4 含空转跳过 + 日报 + 日记 + focus）。
9 点窗口大概率空转不送 LLM，实际增量约 2 次/天。可接受。

## 测试要点

- `parse_schedule`：单时刻、多时刻、非法输入、空值。
- slot 防重：同 slot 不重复触发；错过多个 slot 只补最新一个。
- 水位线：初始化（缺省=昨天 0 点）、推进、跨天窗口。
- `upsert_pattern`：同日重复 upsert 不累加 occurrences、不重复推进 confirmed；跨日正常累加。
- 归属后移：0 点块写昨天日期的日报/日记；守卫标昨天。
